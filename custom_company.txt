# GettingShortlisted.com — Custom Test Company & Job Notification

Implement a **development/staging-only Custom Test Company and Job Posting feature** inside the existing **GettingShortlisted.com** application.

The purpose of this feature is to allow me, as the administrator/developer, to create a fake/custom company and publish a fake job opening so that I can perform a complete end-to-end test of the existing job-alert system.

The most important requirement is:

> **The custom company/job-posting interface must be a separate tab/page inside the SAME GettingShortlisted.com application. It must NOT be a separate application, separate frontend, separate backend, or separate notification system.**

---

## 1. Overall Concept

The application should support two logical areas:

```text
GETTINGSHORTLISTED.COM
│
├── User-facing area
│   ├── Job Preferences
│   ├── Companies Watched
│   ├── Job Dashboard
│   └── Notifications
│
└── Admin/Test area
    ├── Custom/Test Companies
    ├── Create Custom Company
    ├── Create Test Job
    └── Publish Test Job
```

I should be able to have **two browser tabs open simultaneously**:

### Tab 1 — Normal user interface

For example:

```text
Company: TestCorp
Role: Software Engineer
Level: SDE1
Country: India
State: Maharashtra
City: Pune
```

The user subscribes to/watches TestCorp.

### Tab 2 — Admin/Test interface

I open the admin/test tab and:

```text
Create TestCorp
        ↓
Create Job Opening
        ↓
Software Engineer
SDE1
India
Maharashtra
Pune
        ↓
Publish
```

When I publish the job from Tab 2, the backend must process it through the **same job ingestion → normalization → deduplication → matching → notification → queue → email pipeline** used for real jobs.

If the user in Tab 1 matches the job, that user must receive the email notification.

---

# 2. DO NOT Build a Separate System

This requirement is critical.

Do NOT create:

* a separate test application
* a separate test backend
* a separate database
* a separate notification mechanism
* a separate matching engine
* a separate email sender
* a separate subscription system
* a separate Job model
* a shortcut that directly sends an email from the admin UI

The custom/test functionality is simply **another controlled source of jobs**.

The architecture should conceptually be:

```text
Admin/Test UI
      ↓
Create/Publish Custom Job
      ↓
Existing Job Creation/Ingestion Pipeline
      ↓
Normalize
      ↓
Deduplicate
      ↓
Persist Job
      ↓
JOB_CREATED event
      ↓
Existing Matching Engine
      ↓
Find Matching Users
      ↓
Create Notifications
      ↓
Existing Queue
      ↓
Existing Notification Worker
      ↓
Existing Email Provider
      ↓
User Email
```

```text

        ↓

```

Instead:

```text

        ↓
Create/publish Job
        ↓

        ↓

```

# 9. Job Metadata

When a test job is published, it should have the appropriate metadata.

For example:

# 10. Existing Matching Engine MUST Be Reused

This is one of the most important requirements.

Do NOT implement matching logic specifically for test jobs.

The existing matching engine must determine whether a user matches the test job based on their normal preferences.

For example:

```text
User preferences:

Company = TestCorp
Role = Software Engineer
Level = SDE1
Country = India
State = Maharashtra
City = Pune
```

Test job:

```text
Company = TestCorp
Role = Software Engineer
Level = SDE1
Country = India
State = Maharashtra
City = Pune
```

Result:

```text
MATCH
```

Therefore:

```text
Notification created
        ↓
Queued
        ↓
Email sent
```

# 12. Critical Existing-vs-New Job Behavior

Preserve the existing GettingShortlisted.com behavior:

### Scenario A — Job existed before subscription

```text
10:00 AM
TestCorp job is published

10:05 AM
User subscribes to TestCorp
```

The user must **NOT** receive an onboarding notification for the already-existing job.

The job may appear on the user's dashboard according to the existing product behavior.

---

### Scenario B — User subscribes before job is published

```text
10:00 AM
User subscribes to TestCorp

10:05 AM
Admin publishes new TestCorp job
```

If the job matches the user's preferences:

```text
User receives notification
```

This scenario is the primary end-to-end test.

Use the existing subscription timestamp / job first-seen semantics rather than introducing test-specific rules.

# 14. Do Not Bypass the Queue

If the current architecture uses a queue/event system, publishing a test job must put the notification work through the same queue.

Do not implement:

```text
Admin UI → Email API
```

Implement:

```text
Admin UI
   ↓
Backend
   ↓
Job created
   ↓
Event
   ↓
Queue
   ↓
Worker
   ↓
Email provider
```

This is important because the purpose of this feature is to test the **real end-to-end notification system**.

---

# 15. Deduplication

Test jobs must use the same deduplication logic as real jobs.

If the same test job is accidentally processed twice:

```text
JOB_CREATED
JOB_CREATED
```

the system must not send two emails to the same user.

The notification system should remain idempotent.

---

# 16. Admin Authentication / Authorization

The Custom Test Company section must be protected by the application's existing authentication/authorization mechanism.

Only authorized administrators/developers should be able to:

* create test companies
* edit test companies
* create test jobs
* publish test jobs
* trigger test notifications

Do not expose job publishing controls to normal users.

Reuse the existing admin authorization system if one already exists.

# 17. Environment Safety

This functionality is primarily intended for:

```text
development
staging
testing
```

It must be safely gated.

For example:

```text
ALLOW_TEST_COMPANIES=true
```

in development/staging.

Production should default to:

```text
ALLOW_TEST_COMPANIES=false
```

unless explicitly enabled.

Do not allow test data to accidentally generate real production notifications.

If the existing project has an environment/configuration mechanism, integrate with it rather than inventing a second configuration system.

# 28. Most Important Architectural Rule

**Treat the custom company/test job as a synthetic source of a normal job, NOT as a special notification feature.**

The only special part should be how the job enters the system:

```text
REAL WORLD
Company Career Page / ATS
        ↓
Source Adapter
        ↓
Job Pipeline
```

versus:

```text
TEST
GettingShortlisted.com Admin/Test Tab
        ↓
Custom Test Job API
        ↓
Job Pipeline
```

After that point, both paths should converge:

```text
                    ┌── Real Job Source
                    │
                    └── Custom Test Job
                           ↓
                    Job Processing Pipeline
                           ↓
                    Normalization
                           ↓
                    Deduplication
                           ↓
                    Matching
                           ↓
                    Notification
                           ↓
                    Queue
                           ↓
                    Email Worker
                           ↓
                    Email Provider
                           ↓
                       User
```

**Do not create a parallel test pipeline. The purpose of this feature is specifically to validate that the real GettingShortlisted.com job-alert pipeline works end-to-end.**
