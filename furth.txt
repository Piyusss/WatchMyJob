JOBDROP — WHAT TO ADD / MODIFY NEXT
======================================

Scope
-----
This file contains ONLY concrete changes to make next in the existing
JobDrop product: backend changes, frontend/UI changes, and modifications to
existing behavior.

It is intentionally not a general analysis and does not include aspirational
future architecture.

CURRENT PRODUCT BOUNDARY
------------------------
Keep the current core boundary:

    DETECT
      ->
    NORMALIZE
      ->
    DEDUPLICATE
      ->
    CLASSIFY
      ->
    MATCH
      ->
    EMAIL NOTIFY

Email remains the only notification delivery channel for the current phase.

Do NOT add the automated application-assistance system yet.


A. BACKEND — ADD / MODIFY
-------------------------

1. Replace custom authentication with Clerk
--------------------------------------------
Add:
- Clerk authentication
- Google sign-in
- email/password sign-in
- Clerk-managed email verification
- Clerk-managed password reset
- Clerk-managed sessions

Modify:
- Fastify authentication middleware to verify Clerk authentication
- authenticated request context to expose clerkUserId
- local-user resolution: clerkUserId -> User.id

Change User model:
    add clerkUserId UNIQUE

Remove/retire from JobDrop auth:
- passwordHash
- custom password reset implementation
- custom email verification token flow
- custom JWT issuance/session management that Clerk replaces

Keep JobDrop-specific user data:
- email
- name
- phone
- linkedinUrl
- githubUrl
- notificationsPaused
- unsubscribeToken
- createdAt
- updatedAt

2. Add consistent runtime API validation
----------------------------------------
Add validation for all public request bodies and query parameters.

Validate:
- strings and max lengths
- enums
- numeric ranges
- array sizes
- URLs
- company slugs / IDs
- preference combinations
- pagination parameters

Do not rely only on TypeScript compile-time types.

3. Add pagination to jobs API
-----------------------------
Modify:
    GET /api/jobs

to support cursor-based pagination, for example:
    ?limit=30&cursor=...

Do not return the entire active job set in one request.

Update frontend infinite-scroll or paginated loading accordingly.

4. Add/strengthen source request controls
------------------------------------------
For every source adapter:
- request timeout
- bounded retries
- exponential backoff where appropriate
- HTTP 429 handling
- Retry-After handling where supported
- 5xx handling
- malformed-response handling
- schema validation
- response-size safeguards

A source failure must not cause mass job closure.

5. Track successful source freshness
------------------------------------
Ensure each source has:
    lastSuccessfulSyncAt

Keep separate:
    lastAttemptedAt
    lastSuccessfulSyncAt

Expose this information to the internal admin/health layer.

6. Add source sync history
--------------------------
Add a SyncRun / SourceSyncRun table.

Recommended fields:
    id
    sourceId
    startedAt
    finishedAt
    status
    durationMs
    jobsDiscovered
    jobsCreated
    jobsUpdated
    jobsClosed
    jobsReactivated
    error

Record one row per sync attempt.

7. Add operational observability
--------------------------------
Add structured logs and metrics for:

API:
- request count
- latency
- 4xx
- 5xx

Source worker:
- sync attempts
- successful syncs
- failures
- duration
- discovered
- created
- updated
- closed
- reactivated
- consecutive failures

Notification worker:
- queued
- claimed
- sending
- provider accepted
- delivered
- failed
- retried
- dead-lettered

Never log:
- passwords
- Clerk/session secrets
- provider credentials
- unsubscribe tokens
- sensitive personal information unnecessarily

8. Improve notification delivery state
--------------------------------------
Keep:
    QUEUED/SENDING/PROVIDER_ACCEPTED/FAILED/SKIPPED/DEAD_LETTER

Add provider feedback states where useful:
    DELIVERED
    BOUNCED
    COMPLAINED

Record timestamps such as:
    deliveredAt
    bouncedAt
    complainedAt

Suppress permanent hard-bounced email addresses from future sends.

9. Preserve crash-safe notification processing
----------------------------------------------
Keep SENDING persisted before external send.

Keep reconciliation for stuck SENDING rows.

Modify reconciliation carefully so it does not assume true exactly-once external
email delivery.

Treat the delivery model as:
    at-least-once processing with duplicate-risk mitigation

Use:
- durable notification ID
- provider metadata/message identifiers where supported
- conservative reconciliation thresholds

10. Add job lifecycle history
-----------------------------
Add a JobEvent / JobHistory table for meaningful events:

    JOB_CREATED
    JOB_UPDATED
    JOB_CLOSED
    JOB_REACTIVATED
    MATCHING_FIELDS_CHANGED

Store enough information to explain the lifecycle of a job.

11. Add classification diagnostics
----------------------------------
Keep deterministic classification.

Add optional fields such as:
    roleConfidence
    levelConfidence
    opportunityTypeConfidence
    classificationVersion

Optionally store the rule/reason that produced the classification.

Do NOT introduce an LLM into job matching yet.

12. Improve location normalization
----------------------------------
Preserve:
    rawLocation

Normalize where practical into:
    country
    state/region
    city

Handle variants such as:
    Bengaluru / Bangalore
    New York / NYC

13. Add saved-job backend support
--------------------------------
Add:
    SavedJob

Recommended uniqueness:
    UNIQUE(userId, jobId)

Store:
    userId
    jobId
    createdAt

14. Add user/job state
----------------------
Add a separate user-specific job state rather than modifying global Job.status.

Support eventually:
    SAVED
    APPLIED
    DISMISSED

Do not mix:
    Job.status
with:
    User's status toward the job.

15. Add notification history API
--------------------------------
Expose the user's previously created/sent notifications through an authenticated
endpoint.

Example:
    GET /api/notifications

Paginate this endpoint too.

16. Add job detail endpoint
---------------------------
Add:
    GET /api/jobs/:id

Return:
- title
- company
- location
- work mode
- opportunity type
- experience
- description
- postedAt
- firstSeenAt
- updated information
- source
- original application URL
- active/closed state
- match explanation data if appropriate

17. Generate match explanation data
-----------------------------------
Do not make the frontend reverse-engineer why a job matched.

Have the backend provide structured reasons where practical:

    roleMatched
    levelMatched
    experienceMatched
    locationMatched
    workModeMatched
    opportunityTypeMatched

This should be derived from the same canonical matching logic used for
notification eligibility.

18. Add/verify authorization boundaries
---------------------------------------
Verify every user-scoped endpoint.

A user must not be able to:
- read another user's preferences
- alter another user's preferences
- modify another user's company subscriptions
- read another user's notifications
- modify another user's saved/applied/dismissed state

CORE PRINCIPLE
--------------
The next work should make the existing JobDrop system:
- safer
- more observable
- easier to operate
- easier to understand
- easier to act on

Do not make the architecture more complex just to make it look more complex.


separate instructions for UI:

You are now responsible for redesigning and polishing the **JobDrop web UI**.

First, read the existing README/project documentation and inspect the current frontend code carefully. Understand the existing product, routes, components, data flow, and functionality before changing anything.

Your primary goal is to make JobDrop look and feel like a **premium, modern SaaS product**, not like a generic CRUD dashboard.

## DESIGN DIRECTION

The visual quality should be inspired by high-end SaaS products such as:

* Linear
* Vercel
* Stripe
* Raycast
* Arc
* Superhuman
* Resend
* Framer
* modern premium AI/SaaS products

However, do NOT simply copy any one product.

Create a distinct visual identity for JobDrop.

### IMPORTANT: DO NOT DEFAULT TO GENERIC BLACK/WHITE SAAS

Avoid the extremely common:

* black background
* dark gray cards
* white text
* monochrome UI
* excessive gray borders
* generic "developer dashboard" appearance

JobDrop should have a **lighter, more distinctive visual identity**.

Think:

* sophisticated off-white / warm-white surfaces
* very subtle tinted backgrounds
* carefully chosen accent color
* soft gradients
* elegant color transitions
* restrained use of saturation
* premium typography
* layered surfaces
* generous whitespace
* subtle depth
* refined shadows
* beautiful hover/focus states

The result should feel:
**calm + premium + intelligent + modern + trustworthy + slightly playful**

rather than:
**corporate + boring + overly dark + generic + template-like**

## COLOR SYSTEM

Create a coherent design system rather than choosing random colors page by page.

Use:

* warm white / soft neutral background
* slightly tinted secondary surfaces
* dark but not pure-black typography
* one strong primary accent
* one or two supporting accent colors
* subtle success/warning/error colors

The accent should feel distinctive enough that users can recognize JobDrop immediately.

Use gradients very selectively.

Do NOT make every component colorful.

The page should remain elegant and restrained.

## TYPOGRAPHY

Typography is a major part of the design.

Use a high-quality modern sans-serif system and establish a clear hierarchy:

* large expressive hero headline
* strong section headings
* compact but readable UI labels
* excellent body-text readability
* clear metadata typography
* carefully controlled letter spacing

Avoid oversized text everywhere.

Use typography to create hierarchy instead of relying on borders and cards.

## DESIGN PRINCIPLES

Prioritize:

1. Visual hierarchy
2. Whitespace
3. Typography
4. Alignment
5. Consistent spacing
6. Subtle motion
7. Clear information density
8. Excellent responsive behavior

Avoid:

* excessive cards
* excessive borders
* excessive shadows
* unnecessary gradients
* giant rounded rectangles everywhere
* excessive pill-shaped UI
* random animations
* visual clutter
* "dashboard template" aesthetics

A component should only look like a card when it genuinely represents a distinct surface.

## LANDING PAGE

The landing page should feel like a premium SaaS launch site.

The hero should immediately communicate the JobDrop value proposition:

JobDrop watches company career sites and alerts users when relevant jobs appear.

The hero should include:

* strong headline
* concise supporting text
* primary CTA
* secondary CTA where appropriate
* subtle visual product demonstration
* attractive animated background treatment
* company/source credibility

Create a strong visual composition rather than simply stacking text and buttons vertically.

The landing page should contain polished sections such as:

* Hero
* Social proof / company coverage
* How JobDrop works
* Product preview
* Personalization / matching explanation
* Why JobDrop is different
* CTA

Use subtle scroll-based motion and Framer Motion where it adds real value.

## DASHBOARD

The dashboard is the most important authenticated screen.

It should feel like a premium product, not an admin panel.

The visual priority should be:

1. New relevant jobs
2. Search/filter
3. Job cards
4. Useful summary information
5. Company/watch information

Create excellent job cards.

A job card could visually communicate:

* NEW
* Software Engineer
* Figma
* Bengaluru / Remote
* 2–4 years
* Full-time
* discovered recently
* saved state
* apply action

Avoid making every piece of information a badge.

Use typography and spacing intelligently.

Keep settings simple and elegant.

Group:

* Account
* Notifications
* Data
* Security

Use clear hierarchy and whitespace.

Destructive actions such as account deletion should be visually distinct but not visually overwhelming.

## AUTHENTICATION

* Clerk
* Google
* email/password

Design the Clerk integration so that the authentication screens feel consistent with the JobDrop brand.

Do not make the auth experience look like an unrelated third-party template.

## NAVIGATION

Create a refined navigation system.

Authenticated navigation should make these destinations obvious:

* Dashboard
* Companies
* Saved
* Notifications
* Preferences
* Settings

Avoid an overly dense sidebar.

Consider a clean, lightweight SaaS navigation model.

## MICRO-INTERACTIONS

Use Framer Motion deliberately.

Good examples:

* page entrance
* card hover
* subtle scale on interactive elements
* button feedback
* filter transitions
* dropdown animation
* modal transitions
* onboarding transitions
* notification appearance
* skeleton transitions

Do NOT animate everything.

Animations should make the UI feel alive, not distracting.

Use short, polished transitions.

## ICONOGRAPHY

Use lucide-react consistently.

Do not use random icon libraries simultaneously.

Icons should:

* have consistent stroke weight
* have consistent sizing
* support the hierarchy rather than dominate it

## SHADCN / COMPONENT SYSTEM

Continue using shadcn/ui and the existing component architecture.

Do not throw away the component system just to redesign the visuals.

Instead:

* improve the theme
* refine component variants
* create a strong design token system
* improve spacing
* improve typography
* improve states
* improve interaction behavior

Create reusable variants rather than styling every component independently.

## DESIGN TOKENS

Create centralized design tokens for:

* colors
* typography
* spacing
* radius
* shadows
* borders
* transitions
* surfaces

The entire site should look like one coherent product.

## RESPONSIVE DESIGN

The design must be excellent on:

* desktop
* tablet
* mobile

Pay particular attention to:

* dashboard job cards
* filters
* job detail page
* onboarding
* navigation
* company grid
* settings

Do not simply shrink desktop components for mobile.

Design mobile layouts intentionally.

## ACCESSIBILITY

Maintain:

* keyboard navigation
* visible focus states
* semantic HTML
* sufficient text contrast
* accessible labels
* accessible dialogs
* accessible form controls

Premium visual design must not reduce accessibility.

## PERFORMANCE

Do not sacrifice performance for visual effects.

Avoid:

* unnecessary client-side rendering
* huge animation bundles
* expensive effects on every element
* unnecessary re-renders

Use animation where it provides meaningful UX value.

## IMPORTANT PRODUCT RULE

Do not invent new backend functionality merely to make the UI look better.

Use the existing APIs and data model unless a UI requirement clearly needs a backend change.

Where a required backend endpoint does not exist, identify it explicitly instead of faking the behavior.

## IMPORTANT SCOPE RULE

The current JobDrop product ends at:

DETECT
→ NORMALIZE
→ DEDUPLICATE
→ CLASSIFY
→ MATCH
→ EMAIL NOTIFY

Do NOT build the future automated application-assistance experience.

Do NOT add:

* mini application browser
* controlled browser session

* CAPTCHA automation
* automatic application submission

The current frontend should instead make:

a polished and obvious action.

## QUALITY BAR

Do not stop once the UI is merely functional.

Before considering the redesign complete, inspect every page and ask:

* Does this look like a premium SaaS product?
* Is the visual hierarchy obvious?
* Does the page feel spacious?
* Are there too many cards or borders?
* Are colors distinctive?
* Does JobDrop have a recognizable visual identity?
* Do animations feel intentional?
* Does mobile look designed rather than compressed?
* Are empty/loading/error states polished?
* Does every major interaction have proper hover/focus/active states?
* Does the application feel cohesive from landing page through dashboard?

The final result should make someone think:

"This looks like a serious, polished SaaS product."

not:

"This is a functional developer project."

## IMPLEMENTATION APPROACH

Before changing code:

1. Inspect the current frontend structure.
2. Understand all existing routes/components.
3. Preserve existing functionality.
4. Establish the new design system/tokens first.
5. Redesign shared components.
6. Redesign the landing page.
7. Redesign authenticated navigation.
8. Redesign dashboard/job cards.
9. Add/refine job detail.
10. Redesign companies/preferences/settings.
11. Add polished loading/error/empty states.
12. Test desktop and mobile.
13. Remove inconsistent old styling.
14. Ensure all pages feel like the same product.

Do not create a collection of individually beautiful pages that feel unrelated.

The goal is a **single, coherent JobDrop design system**.

Above all, prioritize:
**tasteful visual design + strong UX + consistency + restraint.**
